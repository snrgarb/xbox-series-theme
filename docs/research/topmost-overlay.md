# Research: Topmost Overlay window over running games

Ticket: [#3](https://github.com/snrgarb/xbox-series-theme/issues/3) (part of [#1](https://github.com/snrgarb/xbox-series-theme/issues/1)). Feeds [#8](https://github.com/snrgarb/xbox-series-theme/issues/8) (Overlay + Guide button spike) and [#10](https://github.com/snrgarb/xbox-series-theme/issues/10) (controller input ownership).

**Question.** Can a WPF window from a Playnite 10 Generic extension (.NET Framework 4.6.2, running inside Playnite's process) reliably appear topmost over running games as the **Overlay**, and what are the limits?

## Answer in one paragraph

Yes for the common case, no for the long tail. A WPF window with `Topmost = true` that **takes the foreground** shows reliably over games that run in a **window**: borderless, windowed, and games Windows runs under **Fullscreen Optimizations (FSO)**. That covers almost all DX11/DX12 flip-model games and most Vulkan games on Windows 10/11. When the Overlay is on screen, the DWM simply goes back to composing (it leaves independent flip / MPO), the same as for Game Bar. It **cannot** reliably appear over games in **true exclusive fullscreen** (legacy DX9, DXGI blt-model exclusive, Vulkan `APPLICATION_CONTROLLED` exclusive, or FSO turned off). There, taking focus makes the game drop out of fullscreen, minimise, or lose its device. Only an in-process hook (the Steam/NVIDIA/old-Discord approach) draws over those. The hard part is not z-order. It is **getting the foreground** from a background process when the trigger is a gamepad button, and Windows' foreground lock is designed to stop exactly that. Recommendation: a separate topmost window that takes focus, with an accepted "exclusive fullscreen not supported" limit. No hooking and no band/UIAccess tricks. Details and caveats follow.

## 1. How games present, and what a topmost window does to each

| Game presentation | What a topmost overlay window does | Sources |
|---|---|---|
| **Windowed / borderless, flip model (DX11/12 `FLIP_*`, Vulkan on modern drivers)** | Works. The DWM may be in DirectFlip/independent flip (iFlip), or put the game on an MPO plane. When "other desktop contents come on top" it either transitions back to composed mode, "reverse composes" the contents on top, or uses MPO to stay in independent flip. Visually the overlay shows. You pay a small cost while it is up. | [For best performance, use DXGI flip model § DirectFlip](https://learn.microsoft.com/windows/win32/direct3ddxgi/for-best-performance--use-dxgi-flip-model#directflip) |
| **"Fullscreen" games under FSO** (the game asks for exclusive mode, Windows silently runs it borderless) | Works. Microsoft: FSO is "FSE with the flexibility to go back to DWM composition", and "when an overlay such as the Game Bar is present, the DWM reassumes control of the display." Alt-tab is fast. This is the mode Game Bar relies on. | [Demystifying Full Screen Optimizations (DirectX blog)](https://devblogs.microsoft.com/directx/demystifying-full-screen-optimizations/) |
| **Composition swapchains / windowed blt-model** | Works (always composed). | [Composition swapchain guide § presentation modes](https://learn.microsoft.com/windows/win32/comp_swapchain/comp-swapchain#presentation-modes%E2%80%94composition,-multiplane-overlay,-and-independent-flip) |
| **True exclusive fullscreen, DXGI** (FSO disabled per-exe, or not applied) | Does not work cleanly. "When in full-screen mode, the DWM is disabled." A full-screen swap chain "will relinquish full-screen mode whenever its output window is occluded by another window". So the game drops to windowed (often minimised) as soon as the Overlay appears or takes focus. | [DXGI best practices § Full-screen issues](https://learn.microsoft.com/windows/win32/direct3darticles/dxgi-best-practices#full-screen-issues), [DXGI overview § Presentation](https://learn.microsoft.com/windows/win32/direct3ddxgi/d3d10-graphics-programming-guide-dxgi#presentation) |
| **True exclusive fullscreen, Direct3D 9** | Does not work. The device goes **lost** on "loss of keyboard focus in a full-screen application", and the game must `Reset()` (many old games handle this badly). D3D9Ex never returns `DEVICELOST`, but is still exclusive. | [Lost Devices (Direct3D 9)](https://learn.microsoft.com/windows/win32/direct3d9/lost-devices) |
| **Vulkan with `VK_EXT_full_screen_exclusive`** (`ALLOWED` / `APPLICATION_CONTROLLED`) | Same class as DXGI exclusive. The implementation may "acquire exclusive access to a particular display", and the extension adds `VK_ERROR_FULL_SCREEN_EXCLUSIVE_MODE_LOST_EXT`. Without the extension (default policy), the driver decides, and most Windows drivers present through DXGI/flip, so behaviour matches the borderless row. | [VK_EXT_full_screen_exclusive](https://docs.vulkan.org/refpages/latest/refpages/source/VK_EXT_full_screen_exclusive.html) |
| **OpenGL fullscreen** | Driver-specific. Modern drivers usually present through DXGI interop (flip), so it typically behaves like borderless. Not documented by a first party. Treat as "test". | (no primary source found) |

Microsoft's own direction since the April 2018 Update is that flip-model borderless is "effectively equivalent or better" than exclusive fullscreen ([flip model article](https://learn.microsoft.com/windows/win32/direct3ddxgi/for-best-performance--use-dxgi-flip-model)). Exclusive-only games are mostly older DX9-era titles and games where the user turned off FSO.

**Takeaway:** z-order is not the problem for windowed/FSO games. A plain `Topmost` window is already above every non-topmost window in the desktop band ([Extended Window Styles: WS_EX_TOPMOST](https://learn.microsoft.com/windows/win32/winmsg/extended-window-styles), [WPF windows overview § Window location](https://learn.microsoft.com/dotnet/desktop/wpf/windows/#window-location)). Topmost-vs-topmost ties are broken by activation order, so a game that is itself topmost needs the Overlay to be activated or re-asserted after it.

## 2. How other overlays do it

| Overlay | Technique | Notes | Source |
|---|---|---|---|
| **Steam** | **In-process hook.** "Automatically hooks into any game launched from Steam". Supports DirectX 7–12, OpenGL, Metal, Vulkan. Must hook *device creation* (`SteamAPI_Init` before the D3D/GL device). | Works in exclusive fullscreen because it draws inside the game's own frame. Costs: crashes "due to the way it injects itself", needs the game to "consistently render frames". | [Steamworks: Steam Overlay](https://partner.steamgames.com/doc/features/overlay) |
| **Discord** | Historically an injected hook, like Steam. In April 2024 it rolled out a "revamped Game Overlay" for "stability, reliability, and performance". | Discord's support page (403 to scripted fetch, seen via search snippet) does not document internals. Reports of an out-of-process window design are **unverified** here. | [Discord: Known Issue – Game Overlay](https://support.discord.com/hc/en-us/articles/25289844838551--Known-Issue-Game-Overlay) |
| **NVIDIA (app overlay / ShadowPlay)** | Driver/injection-based. No first-party technical description found. | Not a pattern available to us. | (no primary source found) |
| **Xbox Game Bar** | **Separate composed window, no injection.** Relies on FSO so the DWM can compose it "in a safe and stable way". It has two modes. **Foreground**: Game Bar takes the foreground and receives input. **PinnedOnly**: dismissed; pinned widgets stay visible and can be click-through. | Closest model for the Guide. It is a first-party, system-privileged window (see §3), so it also beats things we can't. | [Demystifying FSO](https://devblogs.microsoft.com/directx/demystifying-full-screen-optimizations/), [XboxGameBarDisplayMode](https://learn.microsoft.com/xbox/game-bar/api/enum-xgb-displaymode), [Click-through your widget](https://learn.microsoft.com/xbox/game-bar/guide/click-through) |
| **Windows Full Screen Experience (handhelds, Xbox Ally)** | Windows has **exclusive access to the Guide button** when FSE is active, and short-press opens Game Bar. View+Menu forwards a Guide press to the focused app. | Relevant edge case: on FSE devices our Guide trigger is pre-empted by the OS. | [Game launchers and handhelds § Game overlays and guide button](https://learn.microsoft.com/gaming/gdk/docs/gdk-dev/pc-dev/handheld/handheld-launchers#game-overlays-and-guide-button) |

The Microsoft FSO post spells out the trade-off: in exclusive fullscreen an overlay must "step into and intercept the rendering process", which "can cause problems including performance regressions, instability and issues with anti-cheat" ([Demystifying FSO](https://devblogs.microsoft.com/directx/demystifying-full-screen-optimizations/)).

**Hooking is ruled out for us.** It needs native code per graphics API (DX9/10/11/12, GL, Vulkan). It risks anti-cheat bans. Steam's own docs say it has to be in place before device creation (we start after the game). And it cannot be built in a .NET Framework Playnite extension without shipping a native injector. That is inappropriate for a public add-on-database release.

## 3. Window bands, UIAccess and `ZBID_SYSTEM_TOOLS`

Since Windows 8, z-order is split into **bands**. Every ordinary window, topmost or not, lives in `ZBID_DESKTOP`. System UI (Start, Action Center, Alt-Tab, Task Manager's always-on-top, Game Bar, the on-screen keyboard) lives in higher bands that always draw above the desktop band. Reverse-engineered order (low to high): `DESKTOP`, `IMMERSIVE_BACKGROUND`, `IMMERSIVE_APPCHROME`, `IMMERSIVE_MOGO`, `IMMERSIVE_INACTIVEMOBODY`, `IMMERSIVE_NOTIFICATION`, `IMMERSIVE_EDGY`, **`SYSTEM_TOOLS`**, `LOCK`, `ABOVELOCK_UX`, `IMMERSIVE_IHM`, `GENUINE_WINDOWS`, **`UIACCESS`** ([ADeltaX, "Window z-order in Windows 10"](https://blog.adeltax.com/window-z-order-in-windows-10/); also [Alia5 (GlosSI author), dev.to](https://dev.to/alia5/overlay-windowsstore-apps-uwp-without-code-signing-2h89)). These are third-party reverse-engineering sources. Microsoft documents none of it.

- `CreateWindowInBand` / `SetWindowBand` are **private user32 exports**. For ordinary processes only `ZBID_DEFAULT`/`ZBID_DESKTOP` succeed, and every other band returns `ERROR_ACCESS_DENIED`. `ZBID_SYSTEM_TOOLS` and the immersive bands need a Microsoft-signed binary with a special `.imrsiv` PE section, or DLL injection into explorer/RuntimeBroker ([ADeltaX](https://blog.adeltax.com/window-z-order-in-windows-10/)). **Not viable** for a public add-on.
- `ZBID_UIACCESS` is reachable with a `uiAccess="true"` manifest. Microsoft documents that such apps "can run as the topmost application in the z-order at any time". But they must be **Authenticode-signed**, installed in a **secure location** (Program Files / System32), and Microsoft says uiAccess "should not be used … by applications that just want to appear above other applications" ([Security Considerations for Assistive Technologies](https://learn.microsoft.com/windows/win32/winauto/uiauto-securityoverview), [UAC secure-location policy](https://learn.microsoft.com/windows/client-management/mdm/policy-csp-localpoliciessecurityoptions#useraccountcontrol%5C_onlyelevateuiaccessapplicationsthatareinstalledinsecurelocations)). A Playnite extension runs inside `Playnite.FullscreenApp.exe`, whose manifest we don't control. So this would need a separate signed helper exe installed outside Playnite's usual `%LocalAppData%` location. That conflicts with a one-click add-on-database Bundle.
- **What bands would buy us:** sitting above UWP/immersive full-screen apps and system UI. Win32 games are in `ZBID_DESKTOP`, so a normal topmost window already sits above them. **We don't need bands for the target scenario.**

## 4. Taking and returning focus without minimising the game

The Overlay must become the **foreground** window so that keyboard focus moves to it and focus-aware games stop reading the pad (§6). Windows restricts this deliberately.

**The rule** ([SetForegroundWindow remarks](https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-setforegroundwindow#remarks)): a process may set the foreground only if no menus are active, the foreground process hasn't called `LockSetForegroundWindow`, **and** one of these holds: it *is* the foreground process, it was started by the foreground process, there is no foreground window, **it received the last input event**, the foreground lock timeout has expired, or a debugger is attached. "It is possible for a process to be denied the right … even if it meets these conditions." Otherwise Windows only flashes the taskbar button. Microsoft's handheld guidance restates it: "background apps can't take the foreground. Windows enforces foreground control as an operating system–level privilege" ([Game launchers and handhelds § Foreground](https://learn.microsoft.com/gaming/gdk/docs/gdk-dev/pc-dev/handheld/handheld-launchers#foreground-and-background-management)).

When the Guide is pressed, Playnite is a background process, and XInput polling does not count as "received the last input event". So a bare `Window.Activate()` / `SetForegroundWindow` **will usually fail** while a game is in front.

Options, from most to least defensible:

1. **Synthesize an Alt key tap, then `SetForegroundWindow`.** Microsoft documents that "the system automatically enables calls to SetForegroundWindow if the user presses the ALT key" ([LockSetForegroundWindow remarks](https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-locksetforegroundwindow)). Injecting Alt down/up with `SendInput` makes the calling process the last-input recipient. This is the widely used workaround, and it relies on documented behaviour. Caveats: `SendInput` "is subject to UIPI" and fails silently into a higher-integrity (elevated) foreground game ([SendInput](https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-sendinput)). Also, a stray Alt can open a game's menu bar or trigger in-game bindings. Send a harmless combination, or Alt immediately followed by a no-op key.
2. **`AttachThreadInput` to the foreground thread, then `SetForegroundWindow`.** This works in practice, but Raymond Chen documents that it can hang both processes, since the two threads then share an input queue ([The dangers of attaching input queues](https://devblogs.microsoft.com/oldnewthing/20080801-00/?p=21393), [2013 follow-up](https://devblogs.microsoft.com/oldnewthing/20130619-00/?p=4043)). A hung game would freeze Playnite. Avoid it, or use it only as a guarded fallback.
3. **Show without activating** (`ShowActivated = false` / `WS_EX_NOACTIVATE`, [Extended Window Styles](https://learn.microsoft.com/windows/win32/winmsg/extended-window-styles)). This always works visually over windowed/FSO games, but the game keeps focus and keeps reading input. Usable only together with §6's alternatives.

**Returning focus.** Capture `GetForegroundWindow()` before showing the Overlay. On close, call `SetForegroundWindow(savedHwnd)`. This is permitted because by then the Overlay *is* the foreground process (rule 2.2). Hide the Overlay *after* handing focus back, so the system doesn't pick an arbitrary next window. Never minimise or restore the game window. For DXGI-exclusive or D3D9 games the damage happens at focus loss, so returning focus can't undo it (§1).

**Elevated games.** If the game runs as admin, our medium-IL process can still be *topmost* over it (z-order is not UIPI-gated). But `SendInput` into it is blocked, so trick 1 fails and the Overlay may show without focus. This is the "games running as admin" edge case from #1. Document it as unsupported unless Playnite itself is elevated.

**FSE devices.** With the Xbox Full Screen Experience active, the taskbar is hidden and Windows owns the Guide button ([handheld guidance](https://learn.microsoft.com/gaming/gdk/docs/gdk-dev/pc-dev/handheld/handheld-launchers#game-overlays-and-guide-button)). Treat it as out of scope (consistent with "not coexisting with Game Bar's Guide binding").

## 5. Transparent and click-through windows in WPF

- `WindowStyle=None` + `AllowsTransparency=true` + transparent `Background` gives a **layered window** with per-pixel alpha, hardware-accelerated on WDDM ([Graphics Rendering Tiers](https://learn.microsoft.com/dotnet/desktop/wpf/advanced/graphics-rendering-tiers#rendering-tier-definitions), [Technology Regions overview](https://learn.microsoft.com/dotnet/desktop/wpf/advanced/technology-regions-overview#regions)). `HwndHost`/WebView-style child HWNDs don't composite into it ([Troubleshooting Hybrid Applications](https://learn.microsoft.com/dotnet/desktop/wpf/advanced/troubleshooting-hybrid-applications#opacity-and-layering)).
- Hit testing on a layered window follows its alpha: zero-alpha pixels pass mouse input through. Adding `WS_EX_TRANSPARENT` makes the whole window click-through ([Window Features § Layered windows](https://learn.microsoft.com/windows/win32/winmsg/window-features#window-types)). Use `WS_EX_TOOLWINDOW` to keep the Overlay out of Alt-Tab and the taskbar ([Extended Window Styles](https://learn.microsoft.com/windows/win32/winmsg/extended-window-styles)).
- For the Guide, click-through is the wrong default. The Guide flyout is modal (it owns the pad while open). The simplest design is a full-screen Overlay with a dimmed scrim plus the flyout, taking focus. Keep a pre-created, hidden Overlay window so it appears in one frame, rather than constructing a WPF window on Guide press. Click-through/no-activate only matters for any later "toast" style UI (e.g. achievement-style notifications), Game Bar's *PinnedOnly* analogue.
- A full-screen layered window forces the DWM out of independent flip while visible (§1). That is fine while the Guide is open, but **hide** (don't just make transparent) the Overlay when the Guide closes, so the game gets iFlip back.

## 6. Keeping controller input from the game while the Guide is open

(Detailed decision belongs to [#10](https://github.com/snrgarb/xbox-series-theme/issues/10). Here are the facts that constrain it.)

- **There is no user-mode way to *steal* an XInput device from another process.** XInput is a shared poll API, so any process can call `XInputGetState`.
- **Focus is the lever.** Microsoft documents that on Windows 10+ "game controller input is automatically enabled/disabled by the system based on the application window focus" (why `XInputEnable` is deprecated) ([XInputEnable](https://learn.microsoft.com/windows/win32/api/xinput/nf-xinput-xinputenable)). GameInput's current docs say input "goes to applications in focus by default", with opt-in `GameInputEnableBackgroundInput` ([GameInput fundamentals § Application Focus](https://learn.microsoft.com/gaming/gdk/docs/features/common/input/overviews/input-fundamentals#application-focus), [GameInputFocusPolicy](https://learn.microsoft.com/gaming/gdk/docs/reference/input/gameinput/enums/gameinputfocuspolicy)). So **if the Overlay takes the foreground, focus-respecting games see neutral input**, and that is exactly why §4 matters.
- **Caveats, which must be verified in the #8 spike:**
  - Behaviour is inconsistent in practice. A 2025 Microsoft Q&A report says `XInputGetState` still returns live buttons when unfocused on Windows 10+, and only rumble is focus-gated ([Q&A](https://learn.microsoft.com/answers/a/12803981)). An older version of the GameInput page said "on PC, input goes to all processes by default". Expect some games (and Playnite itself) to keep reading the pad while unfocused.
  - Games using **Steam Input**, DirectInput/HID, raw input with `RIDEV_INPUTSINK`, or GameInput with background input enabled will **ignore focus by design**.
  - A game using `GameInputExclusiveForegroundGuideButton` can hide Guide presses from us while it is focused ([GameInputFocusPolicy](https://learn.microsoft.com/gaming/gdk/docs/reference/input/gameinput/enums/gameinputfocuspolicy)). That is a #2 concern, noted here because it also limits the Overlay trigger.
- **Mitigations if focus isn't enough:** pausing the game is not ours to do. A driver-level filter (HidHide-style device hiding, or a virtual-controller remap à la ViGEm) is the only *robust* way to keep input away from the game. It needs a kernel driver install, which is out of proportion for a theme Bundle. Recommended stance: **rely on focus, document that some games will still react to the pad while the Guide is open**, and design Guide navigation so stray inputs are harmless (e.g. B closes the Guide, matching Xbox).

## Recommendation

1. **Build the Overlay as a pre-created, hidden, borderless, `Topmost`, `WS_EX_TOOLWINDOW` WPF window inside the extension.** Show it full-screen on the game's monitor when the Guide fires. Use no hooking, no window bands, no uiAccess helper.
2. **Take the foreground** with save-foreground → synthesized-Alt `SendInput` → `SetForegroundWindow` → `Activate`. Verify with `GetForegroundWindow()`. If that fails, fall back to showing un-activated (visible but the game keeps input) rather than `AttachThreadInput`.
3. **On close**, restore the saved HWND to the foreground, then hide the Overlay. Never minimise or restore the game.
4. **Rely on focus to keep pad input from the game.** Accept and document that some games ignore focus.
5. **Declare supported scope:** windowed, borderless and FSO "fullscreen" games (the vast majority on Win10/11). **Unsupported:** true exclusive fullscreen (DX9 exclusive, FSO disabled, Vulkan exclusive), where the game will drop out of fullscreen, minimise, or lose its device when the Guide opens. Also unsupported: elevated games (no focus steal) and FSE handhelds (the OS owns the Guide button). The first-run guidance could suggest borderless/FSO.
6. **#8 spike must measure**, on real titles: (a) foreground success rate with the Alt trick, (b) whether the game sees neutral XInput while the Overlay is focused, (c) the DX9 exclusive and FSO-disabled failure modes, (d) latency from Guide press to first Overlay frame, (e) iFlip restored after close (PresentMon).

## Confidence and gaps

- **High confidence** (Microsoft docs): foreground rules, the Alt exemption, DXGI/D3D9 exclusive behaviour, FSO/Game Bar composition, layered-window hit testing, uiAccess requirements, GameInput focus policy.
- **Medium** (reverse-engineered, single authors): window band order and the `CreateWindowInBand` restrictions.
- **Low / unverified:** Discord's 2024 overlay architecture, NVIDIA overlay internals, OpenGL fullscreen behaviour, and whether XInput is really focus-gated on current Windows 11 builds (the docs and field reports disagree). The spike resolves these empirically.
