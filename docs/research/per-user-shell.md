# Research: A per-user shell that starts Playnite first and explorer later

Ticket: [#99](https://github.com/snrgarb/xbox-series-theme/issues/99), part of the map [#96](https://github.com/snrgarb/xbox-series-theme/issues/96) (boot this TV PC straight into Playnite at Xbox mode speed). Feeds [#103](https://github.com/snrgarb/xbox-series-theme/issues/103) (which route), [#104](https://github.com/snrgarb/xbox-series-theme/issues/104) (when explorer starts, what starts the startup apps) and [#105](https://github.com/snrgarb/xbox-series-theme/issues/105) (keep Playnite up, fall back to the desktop).

**Question.** On Windows 11 Pro Insider 26300.9457 with autologon, how can a per-user shell (`HKCU\Software\Microsoft\Windows NT\CurrentVersion\Winlogon\Shell`, with HKLM left at `explorer.exe`) start Playnite Fullscreen first and explorer later as the full shell, with no admin rights at boot? What has to be handled along the way?

Researched 2026-10-21 from Microsoft Learn, ReactOS's explorer source, Playnite's source, a read-only look at this PC's registry and its shell binaries (`explorer.exe` 10.0.26100.8117, `winlogon.exe` 10.0.26100.8117, `userinit.exe` 26100.9278), and four community projects. Nothing on this PC was changed. Claims that only a real sign-in can settle are marked **TV test** and collected in §8.

**Device form caveat.** This PC still has XFSET 0.9.4 (Xbox FullScreen Experience Tool) in place, as found in [#98](https://github.com/snrgarb/xbox-series-theme/issues/98):
- `HKLM\...\Windows NT\CurrentVersion\OEM\DeviceForm = 46`, so Windows treats it as a gaming handheld;
- ViVe feature IDs 52580392, 50902630 and 59765208 are on;
- SYSTEM boot tasks `XFSET-SetPanelDimensions` and `XFSET-SimulateTouchService` are installed.

The Xbox full screen settings explorer reads at start are currently off (`HKCU\...\GamingConfiguration\StartupToGamingHome = 0`, `GamingHomeApp` empty). #98 rules Xbox mode out, so the per-user shell is the remaining route, and the tool's PC will be a stock **desktop** form once XFSET is removed. The core mechanism (§1, §2) has no known tie to the device form. Its evidence comes from ordinary desktop PCs and ReactOS. What a handheld form could change is flagged where it applies: whether explorer starts the gaming home app, the Welcome-screen timing, cursor and touch behaviour, and the taskbar's tablet layout. The TV tests in §8 are written for the stock desktop form, **after XFSET is removed**.

## Answer in one paragraph

It works, and none of it needs admin. `userinit.exe` starts whatever the HKCU `Shell` value names in place of HKLM's, and the HKCU Winlogon key is writable by the user (§1). When our tool later runs a plain `C:\Windows\explorer.exe`, explorer becomes the full shell, because it checks two things and both hold: no shell window exists yet, and the **machine** (HKLM) `Shell` value names `explorer.exe`. The HKCU value doesn't get in its way. That explorer then runs the Run keys and Startup folder once for the session, after its usual startup delay, because nothing has run them yet (§2). Until explorer runs, the PC has no taskbar, tray, Win+key shortcuts, explorer-hosted toasts, or Store/MSIX app activation. That last one matters for Game Pass ([#100](https://github.com/snrgarb/xbox-series-theme/issues/100)). All of it comes back when explorer starts (§3). With a custom shell, Winlogon most likely drops the Welcome screen almost at once (T3), so the tool's **first** job is a black, cursor-less window that covers the screen. It keeps that window up until Playnite (ideally the Bundle) says Start-up's first frame is on screen. Once explorer is up, Playnite stays in front by being marked full-screen to the taskbar (§4). If explorer is still held back when a Game Pass game is launched, Playnite's Xbox plugin starts `explorer.exe shell:AppsFolder\…` itself, and that explorer most likely becomes the shell then and there. Its startup apps would then start alongside the game. Starting explorer as the shell soon after Start-up's first frame avoids that (§4). Recovery is the tool's own: if Playnite won't stay up, it starts explorer, which is a normal desktop. If the tool itself can't start, Ctrl+Shift+Esc → Run new task → `explorer.exe` gets a full desktop, and deleting one HKCU value undoes everything (§5). Holding Shift at boot only skips autologon. It doesn't skip the shell.

## How the pieces fit

```
power → firmware → kernel → Winlogon (autologon)
  Winlogon desktop: "Welcome" ──┐
  userinit.exe                  │  reads Shell: HKCU Winlogon beats HKLM Winlogon
    └─ starts our tool          │  our exe has no ShellPrograms entry, so userinit signals the
                                ┘  desktop switch itself → Winlogon shows the user's desktop now
our tool (per-user shell, medium integrity)
  1. black topmost window over every monitor, cursor hidden          (§4)
  2. starts Playnite.FullscreenApp.exe                                (§4, #101)
  3. waits for Start-up's first frame, then removes the black window  (§4)
  4. soon after Start-up's first frame, starts C:\Windows\explorer.exe, no arguments  (§1, §4, #104)
       (if it doesn't, Playnite's Xbox plugin will, at the first Game Pass launch, with
        explorer.exe shell:AppsFolder\<PFN>!<AppId>, and that explorer becomes the shell)
       explorer: GetShellWindow()==NULL && HKLM Shell contains explorer.exe → be the shell
       → desktop + taskbar + tray (TaskbarCreated) + ShellExperienceHost
       → Run keys + Startup folder, once per session, after its startup delay   (§2)
  5. keeps watching Playnite (and explorer); if Playnite won't stay up → start explorer (§5, #105)
```

## 1. Becoming the shell

### Which program Windows starts

- **HKCU `Shell` overrides HKLM `Shell` for what userinit launches.** One account's custom shell broke because a stale HKCU `Shell=explorer.exe` was set: "when HKLM is set to some alternate shell, but HKCU is set to explorer.exe, it starts to remove explorer.exe's taskbar (etc.) but then runs explorer.exe, which creates a file explorer window" ([Custom Shell Standard User, Microsoft Q&A archive, 2020](https://learn.microsoft.com/en-us/archive/msdn-technet-forums/05b5d328-f221-4020-8645-84eb39ab4351)). `userinit.exe` on this PC carries both `Software\Microsoft\Windows NT\CurrentVersion\Winlogon` and `Shell`/`DefaultShell` strings, and `%SystemRoot%\Explorer.EXE` as its default.
- **No admin needed.** On this PC, `HKCU\Software\Microsoft\Windows NT\CurrentVersion\Winlogon` grants the user (`garbonsole\gabe`) **FullControl**. The documented per-user alternative is the "Custom User Interface" policy (`HKCU\Software\Microsoft\Windows\CurrentVersion\Policies\System\Shell`, [Policy CSP ADMX_WinLogon/CustomShell](https://learn.microsoft.com/windows/client-management/mdm/policy-csp-admx-winlogon#customshell)), which userinit also reads. But that key is **ReadKey** only for the user here, so it needs admin. Shell Launcher is out too, because it needs Enterprise/Education/IoT ([Shell Launcher overview](https://learn.microsoft.com/windows/configuration/shell-launcher/)) and this PC is Pro.
- **Present values (read-only):** HKLM `Shell = explorer.exe`, `AutoRestartShell = 1`, `AutoAdminLogon = 1`. HKCU `Shell` is not set.

### How explorer decides to be the shell

Explorer becomes the shell (desktop and taskbar) only when **both** of these hold. Otherwise it treats the launch as "open a folder window":

1. **No shell window exists yet.** `GetShellWindow()` "If no Shell process is present, the return value is NULL" ([GetShellWindow](https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-getshellwindow)).
2. **The machine's (HKLM) `Shell` value names `explorer.exe`.** ReactOS fixed its explorer to match Windows ([CORE-19887](https://jira.reactos.org/browse/CORE-19887), commit [df197bc](https://github.com/reactos/reactos/commit/df197bc424f319585a1373ab6d4d033fb938fefb)). Its `IsExplorerSystemShell()` opens **`HKEY_LOCAL_MACHINE`**`\Software\Microsoft\Windows NT\CurrentVersion\Winlogon`, reads `Shell`, and does a case-insensitive substring match on explorer's own file name. `wWinMain` then does `bExplorerIsShell = (GetShellWindow() == NULL) && IsExplorerSystemShell()` ([explorer.cpp L115–148, L277](https://github.com/reactos/reactos/blob/a97c8a2cdcf6a9a7f5cc543951a02ccb7a80d8ca/base/shell/explorer/explorer.cpp#L115-L148)).

ReactOS is a re-implementation, not Windows. There are two pieces of Windows evidence that the check is HKLM rather than HKCU. First, the mirror case quoted above: HKCU `explorer.exe` with HKLM custom made userinit start explorer, and **explorer refused to be the shell**. If explorer read HKCU, it would have seen `explorer.exe` and become the shell. Second, PlayniteShell, an HKLM custom shell, has to flip HKLM `Shell` to `explorer.exe` around `start explorer.exe` to get a desktop ([Desktop.bat L2–6](https://github.com/Blueforcer/PlayniteShell/blob/65b6ffa8f8fa5e897773d60dd5dcacf641300a1c/Desktop.bat#L2-L6)). WindowsHandheldMod, an HKCU shell, just runs `start explorer.exe` (§6). On this PC, `explorer.exe` holds the Winlogon key path next to an `explorer.exe` literal and a `Local\ExplorerIsShellMutex`, which fits a "Shell names me, and I'm the only one" check. For legacy readers, `IniFileMapping\system.ini\boot\Shell` maps to `SYS:Microsoft\Windows NT\CurrentVersion\Winlogon` on this PC, and `SYS:` means HKLM ([GetPrivateProfileString remarks](https://learn.microsoft.com/windows/win32/api/winbase/nf-winbase-getprivateprofilestring#remarks)). So the old `system.ini [boot] shell` lookup also sees only HKLM.

**So the HKCU value doesn't get in the way.** It changes what userinit starts, not what explorer checks. **TV test T1** confirms this on 26300.

### Rules for the tool when it starts explorer

- Run `%WINDIR%\explorer.exe` with **no arguments**. Once a shell exists, any explorer launch, with or without arguments, opens a folder window or hands its arguments to the running shell. While **no** shell exists, the decision in the ReactOS model is made before the command line is looked at, so even `explorer.exe shell:AppsFolder\…` becomes the shell (§4, the Game Pass case). Whether a Windows explorer that became the shell that way also carries out its argument is unknown (T10). The tool uses no arguments so it doesn't depend on that.
- Start it at the tool's own (medium) integrity, and keep it **out of any kill-on-close Job object** the tool uses for Playnite, so explorer doesn't die with the tool. Don't let it inherit handles.
- Start it **once**, and check `GetShellWindow()` first: Playnite's Xbox plugin may already have started it (§4). A second plain `explorer.exe` finds the shell window and opens a File Explorer window. To know which process is the shell, read the owner of `GetShellWindow()` (`GetWindowThreadProcessId`) rather than trusting the tool's own child handle.
- Nothing may register a shell window first (`SetShellWindow`/`Progman`). Playnite doesn't.

## 2. Startup apps when explorer starts late

- **Explorer runs them, nothing else does.** Microsoft's Shell Launcher docs say Shell Launcher "processes the `Run` and `RunOnce` registry keys before starting the custom shell, so your custom shell doesn't need to handle the automatic startup" ([Configure Shell Launcher](https://learn.microsoft.com/windows/configuration/shell-launcher/configure#shell-launcher-startup-and-exit-behavior)). A plain Winlogon `Shell` swap gets no such help, so **until explorer runs, no Run key, RunOnce or Startup folder entry runs.** Startup apps are those three mechanisms ([Startup apps](https://learn.microsoft.com/windows/win32/w8cookbook/startup-apps)). MSIX/UWP StartupTasks are activated by explorer too (`Windows.ApplicationModel.Internal.StartupTaskActivator` in `explorer.exe`).
- **A late explorer still runs them once.** Explorer guards startup runs with per-session volatile markers under `HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\SessionInfo\<session>`. This PC's current session (1) has `RunStuffHasBeenRun` (Run keys) and `StartupHasBeenRun` (Startup folders), along with `UserInitHasBeenRun`, `LogonSoundHasBeenPlayed` and `DesktopSwitchCompleted`. If a marker exists, explorer skips that step. If not, it sets the marker when it starts and runs the step ([Hexacorn, Beyond good ol' Run key, Part 104](https://www.hexacorn.com/blog/?p=5992); the marker names are also strings in this build's `explorer.exe`). Nothing sets them before explorer, so the **first** explorer in the session runs everything, however late it starts. A restarted explorer (after a crash) **won't** run them again. **TV test T2.**
- **Startup delay.** Microsoft: "the system may choose to delay the execution of programs in the `Run` key and in the Startup group to a time when they are less likely to interfere with the foreground user experience" ([Run and RunOnce Registry Keys](https://learn.microsoft.com/windows/win32/setupapi/run-and-runonce-registry-keys)). The knobs are `HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\Serialize\StartupDelayInMSec` and `WaitForIdleState` (DWORDs, both strings in this build's `explorer.exe`). Microsoft doesn't document them. Community write-ups give a default of about 10 s and say 0 turns the delay off ([ElevenForum tutorial](https://www.elevenforum.com/t/enable-or-disable-delay-of-running-startup-apps-in-windows-11.9144/)). The `Serialize` key **doesn't exist** on this PC, so the default applies. In the 21:15 baseline, explorer started at 21:15:26 and Discord at 21:15:32. The delay presumably counts from explorer's own start, not from sign-in. **TV test T2.** The value is in HKCU, so no admin is needed to change it.
- **Order isn't controllable through explorer.** "If more than one program is registered under any particular key, the order in which those programs run is indeterminate" ([Run and RunOnce Registry Keys](https://learn.microsoft.com/windows/win32/setupapi/run-and-runonce-registry-keys)). Explorer does Run keys before Startup folders (Hexacorn). Windows' own "Start when exiting to desktop" hold-back only works inside Xbox mode ([#98](https://github.com/snrgarb/xbox-series-theme/issues/98)), and #98 ruled Xbox mode out. So **the tool has to hold startup apps back and order them itself**, in two parts:
  - **Every app trails Start-up:** the tool starts explorer only after Start-up's first frame. Nothing runs before explorer does, so everything explorer launches trails by construction.
  - **Steam, Discord and Spotify first:** the tool starts those three itself, before it starts explorer, with their explorer entries switched off in Startup apps. For HKCU Run entries that means `HKCU\...\Explorer\StartupApproved\Run`, which is user-writable and is what Task Manager writes. For `DiscordMini.lnk` it means removing the shortcut or switching it off in `StartupApproved\StartupFolder`.
  - Explorer then runs the rest after its delay. The HKLM Run entries here (`SecurityHealth`, `RtkAudUService`, two Logitech assistants, `StartAUEP`) can only be switched off with admin (`HKLM\...\StartupApproved\Run`), so they simply run when explorer starts, which is still after Start-up.
- **The existing Playnite shortcut must go.** The Startup folder holds `Playnite.lnk` → `Playnite.DesktopApp.exe --hidesplashscreen`. If explorer runs it while Fullscreen is already up, Playnite's `CheckOtherInstances` sees a running Playnite with a different process name and sends **`SwitchMode "desktop"`**. That flips the running Playnite into **Desktop mode** ([PlayniteApplication.cs L1006–L1017](https://github.com/JosefNemec/Playnite/blob/3e8abb241873e326e27c75b59dd0d2ea367698e3/source/Playnite/App/PlayniteApplication.cs#L1006-L1017)). The tool's setup must remove that shortcut. Discord is also listed twice: `DiscordMini.lnk` in the Startup folder and `Discord` in HKCU Run.
- `RunOnce` also needs explorer, and the HKLM one only runs for administrators ([Run and RunOnce Registry Keys](https://learn.microsoft.com/windows/win32/setupapi/run-and-runonce-registry-keys)). This user is an admin with a split token. Logon-triggered **scheduled tasks** don't need explorer, because Task Scheduler is a service.

## 4. No desktop flash

### Sign-in to the tool's first frame

- Winlogon shows the Welcome screen on its own desktop until the shell signals **`ShellDesktopSwitchEvent`**, or until **`DelayedDesktopSwitchTimeout`** runs out. That value lives in `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System` and isn't set here. KB 940452 describes the default wait as 30 s ([KB 940452](https://learn.microsoft.com/troubleshoot/windows-server/user-profiles-and-logon/welcome-screen-displayed-for-30-seconds)). Both names are strings in `winlogon.exe`.
- Explorer signals the event when its desktop is ready (`ShellDesktopSwitchEvent` is a string in `explorer.exe`, and ReactOS's explorer sets its ready event after creating the desktop). That is why the Welcome screen lasts until the taskbar paints today. For other shells, **userinit** decides. It reads `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon\ShellPrograms\<exe>\HandlesShellDesktopSwitchEvent` and calls `SetShellDesktopSwitchEvent` itself (strings in `userinit.exe`). Here only `ShellAppRuntime.exe` claims that flag. So for our tool, userinit almost certainly lets Winlogon **switch to the user's desktop right after starting the tool**, before the tool has drawn anything. **TV test T3** checks what fills that gap (black, wallpaper, cursor) and for how long.
- **What the tool must do first:** create a borderless, topmost black window that covers every monitor and hides the cursor, as its very first act, before it starts Playnite or reads settings. Then `UpdateWindow` it and set the session event `ShellDesktopSwitchEvent` itself (`OpenEvent(EVENT_MODIFY_STATE, FALSE, L"ShellDesktopSwitchEvent")` + `SetEvent`), as AnyFSE does (§6). If userinit has already set it, that does nothing. If Winlogon is still waiting, the Welcome screen ends exactly when the black window is ready. Startup cost matters here. A small native exe gets a window up in milliseconds, while a .NET Framework JIT start takes noticeably longer. This feeds "What the tool is".
- **Undocumented alternative (needs admin once, at setup):** add `ShellPrograms\<tool>.exe\HandlesShellDesktopSwitchEvent = 1`. Winlogon then keeps the Welcome screen until the tool sets `ShellDesktopSwitchEvent` (or the timeout passes), so the switch can be held until Playnite is on screen. It's undocumented, it needs an HKLM write, and the Welcome screen isn't black. Keep it for the spike only if T3 shows an ugly gap.

### Black window to Start-up

- The tool starts **`Playnite.FullscreenApp.exe`** directly, not the `DesktopApp --hidesplashscreen` hop the baseline uses ([#101](https://github.com/snrgarb/xbox-series-theme/issues/101)).
- **Foreground:** the tool's black window is the foreground window, and a process "started by the foreground process" may take the foreground ([SetForegroundWindow remarks](https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-setforegroundwindow#remarks)). So Playnite can activate its own window. The tool can also call `AllowSetForegroundWindow(playnitePid)`.
- **When to drop the black window:** not when Playnite's process starts, and not when its first window appears, because both come before the theme has drawn. The clean signal is the **Bundle**, which runs in Playnite's process and knows when Start-up's first frame (the Boot video) is up. It sets a named event, the tool waits on it with a timeout, then destroys its window. If the timeout runs out, it falls back to "Playnite's main window is visible + N ms".

### Explorer coming up behind Playnite

- Explorer's desktop window sits at the bottom of the z-order. The **taskbar** is topmost, but the shell drops it below a full-screen active window. That detection is automatic but "not as reliable as" **`ITaskbarList2::MarkFullscreenWindow(hwnd, TRUE)`**, after which "the taskbar is moved to the bottom of the z-order when this window is active" ([MarkFullscreenWindow](https://learn.microsoft.com/windows/win32/api/shobjidl_core/nf-shobjidl_core-itaskbarlist2-markfullscreenwindow), [ITaskbarList2](https://learn.microsoft.com/windows/win32/api/shobjidl_core/nn-shobjidl_core-itaskbarlist2)). The taskbar doesn't exist until explorer runs, so the **Bundle** should make this call on its Fullscreen window when it receives the `TaskbarCreated` broadcast (and again on each broadcast). This PC also has taskbar auto-hide on (`StuckRects3` byte 8 = 3).
- **Focus:** explorer may take the foreground while it starts. That is **TV test T5**. If it does, the Bundle can take the foreground back with the Alt-tap + `SetForegroundWindow` routine from [#3](https://github.com/snrgarb/xbox-series-theme/issues/3)/[#51](https://github.com/snrgarb/xbox-series-theme/issues/51) on `TaskbarCreated`. Avoid `LockSetForegroundWindow`: it would also block games launched from Playnite from coming to the front.
- **Other things explorer can show at start:** reopened folder windows (`PersistBrowsers`, unset here), "restart my apps" (`RestartApps`, unset here), and the logon sound (`DisableStartupSound = 1` here, so silent). After a feature update, the full-screen "Let's finish setting up your device" page can appear when explorer starts. That goes on the map's "Updates" watch list.

### The first Game Pass launch while explorer is still held back

- **What starts explorer then.** Playnite's Xbox plugin launches Game Pass (GDK) games with `explorer.exe shell:AppsFolder\<PFN>!<AppId>`, and package activation needs explorer running as the shell. Without it, Windows has `0x80270257`, "The app manager is required to activate applications, but is not running" ([#100 findings](https://github.com/snrgarb/xbox-series-theme/blob/research/game-pass-without-explorer/docs/research/game-pass-without-explorer.md)). With HKCU `Shell` = the tool, HKLM = `explorer.exe` and no shell window yet, that explorer passes both checks in §1, so it **most likely becomes the full shell** right at the first Game Pass launch: desktop, taskbar, tray, ShellExperienceHost and the startup run (§2). Two things are unknown: whether it then also activates the game, or the first launch is lost and must be repeated, and how long activation takes while the app manager comes up. Those are T10 here and T2/T3 in #100.
- **On screen at that moment:** Playnite's Fullscreen window is in front. Explorer's desktop goes to the bottom of the z-order, and the taskbar is topmost but auto-hidden here. The Bundle's `TaskbarCreated` → `MarkFullscreenWindow` handling covers this moment exactly as it covers a tool-started explorer, **as long as it hangs off the broadcast** and not off the tool's own launch. Then the game's bootstrapper splash takes the foreground. The risk is explorer's own start-up work taking the foreground in the same seconds (first-run pages, reopened windows, a startup app's window), which would leave the splash or game behind or unfocused. That is T10.
- **That explorer is Playnite's child, not the tool's.** The tool has to recognise it through `GetShellWindow()` (§1) for its explorer watch and its "start explorer" step, or it would start a second one and open a File Explorer window.

### Explorer soon after Start-up versus on demand

- **On demand (at the first Game Pass launch).** Explorer's once-per-session startup run (§2) fires then. Every Run-key and Startup-folder app that is still switched on starts about `StartupDelayInMSec` (around 10 s by default) after explorer, which is **while the bootstrapper and the game are loading**:
  - they compete for disk and CPU;
  - they can pop windows, update prompts or toasts and take the foreground; AnyFSE had to refocus its launcher after startup apps stole focus ([#88](https://github.com/ashpynov/AnyFSE/issues/88));
  - the first launch also pays explorer's own start-up cost before activation can work;
  - in a session with no Game Pass launch, those apps **never start**, unless the tool starts them.
- **As the shell soon after Start-up's first frame** (for example when the Boot video ends, as #100 suggests):
  - the startup burst lands on Who's playing today?/Home, before any game, and is over by the time one starts;
  - Playnite's later `explorer.exe shell:AppsFolder\…` just hands off to the running shell;
  - Game Pass launches need no guard.
  - The cost is that the burst overlaps the menus. `StartupDelayInMSec` (HKCU) and explorer's own start time can push it later.
- **If on demand is kept anyway:** switch off every startup entry explorer would run, so that an on-demand explorer starts nothing alongside the game. HKCU entries go through `StartupApproved`, which needs no admin. The five HKLM Run entries need admin to switch off, or they will still start with the game. The tool then starts the wanted apps itself, and #100's `OnGameStarting` guard starts explorer and waits for it to be ready before the plugin's explorer command runs.

## 5. Recovery and the fail-safe

| Situation | Way out | Basis |
|---|---|---|
| Playnite won't start or keeps crashing | **The tool's own fail-safe.** If no Playnite window shows within N s, or Playnite exits K times in M minutes, the tool drops the black window, starts `explorer.exe` (a normal desktop, §1) and stops restarting Playnite. Wrap the tool's main loop so any unhandled error also ends in "start explorer". | Same mechanism as the normal path |
| Tool crashes after start-up | Whether Winlogon restarts a non-explorer shell is **unknown**. `AutoRestartShell = 1` here, but Microsoft's Server Core docs (a cmd.exe shell) say that after closing all command prompts you start a new one from Task Manager or sign out and in again ([Manage a Server Core server](https://learn.microsoft.com/windows-server/administration/server-core/server-core-manage)), which suggests no auto-restart. Keep the tool tiny. Playnite and explorer keep running if it dies. **TV test T6.** | Unverified |
| Tool can't start at all (bad path, missing runtime) | Most likely a black screen with a cursor. Whether userinit falls back to explorer is unknown (**TV test T8**). **Ctrl+Shift+Esc → Run new task → `explorer.exe`** gives the full desktop, because HKLM is explorer and there's no shell window. Then `reg delete "HKCU\Software\Microsoft\Windows NT\CurrentVersion\Winlogon" /v Shell /f`. | Docs (Task Manager route) + §1 |
| No keyboard at the TV | The PC is controller-only, so a keyboard must be at hand for the row above. Better: the tool watches the pad itself. A held chord (for example View+Menu for 5 s) starts explorer and, on a second hold, clears the `Shell` value. | Idea for the spec |
| Hold **Shift** at boot | Only bypasses **AutoAdminLogon**: "press and hold the Shift key after you log off or after Windows restarts" ([Turn on automatic logon](https://learn.microsoft.com/troubleshoot/windows-server/user-profiles-and-logon/turn-on-automatic-logon)). Hold it **before** restarting ([KB 2840544](https://learn.microsoft.com/troubleshoot/windows-client/user-profiles-and-logon/hold-shift-key-shutting-down-not-disable-automatic-logon)). Signing in as the same user still runs the HKCU shell, so **Shift alone is not a bypass**. It's useful together with a second account. | Confirmed (docs) |
| Another account | The value is per-user (the policy equivalent is user-scoped, [CustomShell](https://learn.microsoft.com/windows/client-management/mdm/policy-csp-admx-winlogon#customshell)), so a second local admin account signs in to a normal explorer desktop. From there it can `reg load HKU\gabe C:\Users\gabe\NTUSER.DAT` and delete `Shell`. Creating that account is a one-time setup step, not a boot-time change. | Confirmed (per-user scope) |
| Safe Mode | **Safe Mode with Command Prompt** uses `HKLM\SYSTEM\CurrentControlSet\Control\SafeBoot\AlternateShell` (`cmd.exe` here). userinit reads `UseAlternateShell`/`AlternateShell`, and from cmd you can `reg delete` the value. Whether **plain** Safe Mode honours the HKCU shell is unverified. Both need WinRE and a keyboard, so this is a last resort. | Registry + strings, unverified for plain Safe Mode |
| Undo | Delete one HKCU value, restore `Playnite.lnk` and any Startup apps switches, and sign out. No admin needed. | §1 |

**Worth borrowing:**
- **Paint the black window, then `SetEvent(OpenEvent(EVENT_MODIFY_STATE, FALSE, L"ShellDesktopSwitchEvent"))`.** It's harmless if userinit already set it, and it ends the Welcome screen the moment our window is ready. AnyFSE does this under FSE. Whether it changes anything under a Winlogon shell is part of T3.
- Treat "Playnite is up" as any Playnite process or window, not just Fullscreen.
- Clear `safestart.flag` (see §7, #105).
- Refocus Playnite after anything else starts.
- Use `TaskbarCreated` as the "explorer is up" signal.
- Fall back to `explorer.exe` from inside the shell.

**Pitfalls seen:** fixed sleeps instead of signals; `tasklist`-based checks that always succeed; no crash recovery at all; killing explorer, which loses the tray, toasts and startup apps; antivirus flags on batch-to-exe output. AnyFSE issue [#83](https://github.com/ashpynov/AnyFSE/issues/83) reports that on Insider **26300.8170** FSE became "Xbox mode" and the home-app picker was removed. That agrees with [#98](https://github.com/snrgarb/xbox-series-theme/issues/98), which ruled the home-app route out. A Winlogon shell also looks less exposed to that churn. No project reports HKCU `Shell` being ignored on 24H2, 25H2 or Insider builds, and none tested it either.

## 7. What this means for the map

- **[#103](https://github.com/snrgarb/xbox-series-theme/issues/103) (route):** #98 ruled out Xbox mode, which leaves the per-user shell. It is viable with **no admin at boot or at setup** (HKCU only). The admin-only extras are optional: the ShellPrograms desktop-switch flag, switching off HKLM Run entries, and a second admin account for recovery. Removing XFSET (handheld `DeviceForm`, ViVe IDs, boot tasks) is a one-time setup step before the TV tests.
- **[#104](https://github.com/snrgarb/xbox-series-theme/issues/104) (when explorer starts, what starts the startup apps):** whenever the tool starts explorer, explorer runs every startup app once, in an indeterminate order, after `StartupDelayInMSec`. Windows' "Start when exiting to desktop" exists only in Xbox mode, which #98 ruled out, so the tool holds back and orders startup apps itself. Starting explorer after Start-up's first frame makes every app trail. The tool launches Steam, Discord and Spotify itself first, with those entries switched off in Startup apps (HKCU, no admin). `Playnite.lnk` must leave the Startup folder.
- **[#100](https://github.com/snrgarb/xbox-series-theme/issues/100) (Game Pass):** #100 confirmed that Store/MSIX activation needs explorer as the shell. With explorer held back, the plugin's own `explorer.exe shell:AppsFolder\…` most likely becomes the shell at the first Game Pass launch, so "on demand" happens by itself, at the worst moment: the startup apps start alongside the game, and it's unknown whether the game launches on that first try (T10). **Starting explorer as the shell soon after Start-up's first frame is the better choice** (§4). If on demand is kept, switch off every startup entry and guard the launch.
- **[#105](https://github.com/snrgarb/xbox-series-theme/issues/105) (keep Playnite up, fall back):** the tool is the watchdog. Windows probably won't restart it. Watch for "**Playnite is up**", not just for the Fullscreen process. Playnite's "Switch to Desktop mode" is `QuitAndStart(DesktopExecutablePath)` ([FullscreenAppViewModel.cs L742–L781](https://github.com/JosefNemec/Playnite/blob/3e8abb241873e326e27c75b59dd0d2ea367698e3/source/Playnite.FullscreenApp/ViewModels/FullscreenAppViewModel.cs#L742-L781)), and both modes hold the mutex `PlayniteInstaceMutex` ([PlayniteApplication.cs L38, L155](https://github.com/JosefNemec/Playnite/blob/3e8abb241873e326e27c75b59dd0d2ea367698e3/source/Playnite/App/PlayniteApplication.cs#L38)). A watchdog that relaunched Fullscreen whenever `Playnite.FullscreenApp.exe` vanished would undo a deliberate switch to Desktop mode. A watchdog must only ever launch `FullscreenApp`, never `DesktopApp` (§2). It should also restart explorer if explorer dies after it has become the shell (T6). **Crash relaunch trap:** Playnite writes `safestart.flag` at start and deletes it once started. If the flag survives a crash during start-up, the next launch shows a **"start in safe mode?" MessageBox** ([PlayniteApplication.cs L132–L146](https://github.com/JosefNemec/Playnite/blob/3e8abb241873e326e27c75b59dd0d2ea367698e3/source/Playnite/App/PlayniteApplication.cs#L132-L146)). That box would sit behind the tool's black window on a controller-only TV. Either clear the flag before relaunching, as AnyFSE does, or keep the black window's timeout short and drop it when Playnite shows any window.
- **"Black screen to Start-up" (fog):** mostly specifiable now. Tool black window first → Playnite Fullscreen → Bundle's first-frame event → drop the window → explorer later, with the Bundle calling `MarkFullscreenWindow` on `TaskbarCreated`, whoever started explorer. The open part is the few frames between the Welcome screen and the tool's window (T3), plus focus when explorer starts (T5) or when it starts at a Game Pass launch (T10).
- **"What the tool is" (fog):** it must get a window up in milliseconds, so a small native exe (or an AOT-compiled one) beats a .NET Framework JIT start for at least the first stage. Its `Shell` value is just its own path in HKCU.
- **"Updates" (fog):** add to the watch list the HKCU `Shell` value, `ShellAppRuntime` being switched on, Serialize values, and the first-run page after feature updates.

## 8. Tests to run on the TV

Run these on the **stock desktop form, after XFSET is removed**: `DeviceForm` back to its original value or deleted, the three ViVe IDs off, and the `XFSET-*` boot tasks gone. On a handheld-flagged PC, explorer and the logon path may behave differently. For example, explorer may start the gaming home app if `StartupToGamingHome` is ever 1, `SimulateTouchService` can hide the cursor through cursor suppression (`EnableCursorSuppression = 1` here), and the taskbar may take its tablet layout. If any test has to run before XFSET comes off, log `DeviceForm` and `StartupToGamingHome` with the result and treat it as provisional.

Before any of these, keep a keyboard plugged in and know the way back: **Ctrl+Shift+Esc → Run new task → `explorer.exe`**, then `reg delete "HKCU\Software\Microsoft\Windows NT\CurrentVersion\Winlogon" /v Shell /f`. Each test sets HKCU `Shell` to a small test harness and signs out and in (or cold boots).

- **T1, explorer becomes the shell.** Harness: black window, start Playnite Fullscreen, wait 20 s, start `C:\Windows\explorer.exe` with no args. Expect the taskbar (auto-hidden) and the desktop, **no folder window**, no Xbox app or gaming home app, `explorer.exe`'s parent = the harness, and `GetShellWindow()` owned by explorer. Fail if a File Explorer window opens.
- **T2, startup apps after a late explorer.** In the same run, log process start times for explorer, Steam, Discord and Spotify, and watch `HKCU\...\Explorer\SessionInfo\<session>\RunStuffHasBeenRun` / `StartupHasBeenRun` appear only after explorer starts. Repeat with `Serialize\StartupDelayInMSec = 0` to measure the delay. Then kill and restart explorer and confirm the apps **don't** start again.
- **T3, the gap before the tool's window.** Harness with a deliberate 2 s sleep before its window, filmed at 60 fps or screenshotted via Orca. Record the screen between Welcome and the harness window (black? wallpaper? cursor?) and its length. Then run with no sleep to see the real gap.
- **T4, what's missing without explorer.** With only the harness and Playnite running, try: Win+R, Win+G, the pad's Guide button (does Game Bar react?), volume keys, a Discord toast, `start ms-settings:`, and launching a Game Pass game from Playnite. Repeat after explorer starts.
- **T5, focus when explorer arrives.** Log `GetForegroundWindow()` owner every 100 ms from 1 s before explorer starts to 10 s after. Does Playnite keep the pad and the foreground? Is the taskbar ever drawn over it? Repeat with the Bundle calling `MarkFullscreenWindow` on `TaskbarCreated`.
- **T6, who restarts what.** Kill the harness from Task Manager: does Windows restart it (`AutoRestartShell`)? After explorer is the shell, kill explorer: does Windows restart it, and does it come back as the shell?
- **T7, fail-safe.** Point the harness's Playnite path at a non-existent exe. Expect the harness to give up after its limit and bring up a normal desktop through explorer.
- **T8, broken shell path.** Set HKCU `Shell` to a non-existent exe. Record what shows (black? explorer fallback? error?) and confirm the Ctrl+Shift+Esc route works.
- **T9, Shift at boot.** Hold Shift through restart. Expect the sign-in screen, and signing in as gabe still runs the harness.
- **T10, first Game Pass launch with no explorer** (together with #100's T2/T3). Harness without the explorer step, Playnite up, Steam/Discord/Spotify and the other startup entries left on. Launch a Game Pass game from Playnite. Record:
  - does Playnite's `explorer.exe shell:AppsFolder\…` become the shell (taskbar, `GetShellWindow()` owner = that explorer, parent = Playnite)?
  - does the game start on that first launch, and after how long?
  - when do the startup apps start relative to the game's splash?
  - the foreground owner every 100 ms. Does the splash or game ever end up behind Playnite or a startup app's window?
  Then repeat with explorer started by the harness 10 s after Playnite's first frame, and compare.

## Confidence and gaps

- **Confirmed (Microsoft docs, or read on this PC):** HKCU Winlogon is user-writable and the policy key isn't. Explorer runs the startup apps, may delay them, and their order is indeterminate. `TaskbarCreated` re-add. `MarkFullscreenWindow`. `GetShellWindow` is NULL without a shell. Shift only skips autologon. Task Manager → `explorer.exe` recovery. Playnite's second-instance mode switch.
- **Strong, but from a re-implementation or a single report:** explorer's "HKLM `Shell` must name explorer" check (ReactOS source plus the 2020 mirror-case report), and the SessionInfo run-once markers (Hexacorn plus this PC's registry and binary strings).
- **Inferred from binary strings, undocumented:** userinit signals the desktop switch for shells without the `ShellPrograms` flag, and the `ShellPrograms`/`AppResolverHostProcess` role for app activation.
- **Unknown until a TV test:** what the bare desktop shows (T3), explorer-free toasts and flyouts (T4), focus on explorer start (T5), whether Playnite's `shell:AppsFolder` explorer becomes the shell and still launches the game (T10), shell auto-restart (T6), userinit fallback on a bad path (T8), plain Safe Mode.
- **Device form:** the registry reads and binary strings come from this PC while it is handheld-flagged by XFSET. The registry *values* that depend on that (`DeviceForm`, the gaming configuration) are named above. The binaries and the `ShellPrograms`/`IniFileMapping`/`SessionInfo` layout are the same on any 26300 install. AnyFSE's `ShellDesktopSwitchEvent` evidence was gathered under FSE, a handheld form, so T3 re-checks it on the desktop form.
